01  项目简介

LIVA 是一个针对 IoT 固件 ELF 二进制的全自动漏洞挖掘管线。给定一个路由器/嵌入式设备的固件压缩包（或已解包的 ELF 文件），LIVA 按顺序完成：依赖库解析 → 源参数识别 → 危险 Sink 识别 → 危险函数调用图构建 → LLM 污点追踪 → 漏洞推断，最终输出可能的命令注入/缓冲区溢出漏洞报告。

本仓库是经过 macOS 适配改造后的版本：所有 LLM 调用改为兼容 OpenAI 协议的中转 API（api.gpt.ge），IDA Pro 反编译步骤改为调用本机 IDA-MCP 项目（命名管道 IPC），Neo4j 图数据库依赖被完全移除，用轻量的内存路径查找替代。

elf  — 依赖解析

用 pyelftools 读取 ELF 动态段，找出所有 .so 依赖，在 search_dir 中定位文件路径，检测已知危险函数。输出写入 result/ 目录。

📥

source  — 外部输入入口

Ghidra 静态分析找出可能的用户输入函数（nvram_get、websGetVar 等），IDA-MCP 对它们逐一反编译，然后发送给 LLM 判断哪些是真正的数据源。

🎯

sink  — 危险函数

Ghidra 分析从已知危险函数（system/strcpy/sprintf…）向上找调用链，IDA-MCP 反编译调用链上的函数，LLM 判断是否存在数据传入路径。

🗺️

danger  — 调用图

Ghidra DangerFlowAnalyzer.java 输出 parent_child_calls.json（谁调用了谁），IDA-MCP 对每个父函数地址反编译，追加 decompiled_c 字段。

🧵

taint  — 污点追踪

从 danger 阶段的反编译结果中提取参数传递片段，调用 Fine-tuning LLM（DeepSeek）分析参数映射关系，输出结构化的污点分析 JSON。

⚡

infer  — 漏洞推断

SimplePathFinder 在内存中对比 source / sink 函数集合，找出同时调用两者的父函数。VulInfer 拼装代码报告，LLM 最终判断是否存在命令注入或缓冲区溢出。

03  如何运行

前置条件

  • ✅IDA Pro 9.x 已安装于 /Applications/IDA Professional 9.3.app，并已在 IDA 中打开目标二进制（主程序 + 所有 .so 库），每个打开的文件会生成一个 IDA-MCP 会话
  • ✅IDA-MCP 项目位于 /Users/yangshuangning/VscodeProjects/ida-mcp-main
  • ✅Ghidra 位于 LIVA-main/ghidra/support/analyzeHeadless（已包含在项目目录中）
  • ✅conda 环境 iotreaper 已创建（见下方安装命令）
  • ✅中转 API Key 已配置到 config/config.ini 的 [LLM] 和 [Fine-tuning] 段

Step 1  — 安装环境

# 进入项目目录
cd /Users/yangshuangning/VscodeProjects/LIVA-main

# 用 conda 创建环境（若已有则跳过）
conda create -n iotreaper python=3.11 -y
conda activate iotreaper

# 安装依赖
pip install openai pyelftools

Step 2  — 配置 config.ini

# config/config.ini 中需要修改的关键字段：

[LLM]
api_key = sk-你的中转API密钥
base_url = https://api.gpt.ge/v1   # 或其他 OpenAI 兼容端点
model   = deepseek-v3

[Fine-tuning]
api_key = sk-你的中转API密钥
base_url = https://api.gpt.ge/v1

[IDAMCP]
ida_mcp_path = /Users/yangshuangning/VscodeProjects/ida-mcp-main
ida_dir      = /Applications/IDA Professional 9.3.app

Step 3  — 运行完整管线

conda run -n iotreaper python3 liva.py \
    /path/to/firmware/jhttpd \     # 主 ELF 文件绝对路径
    /path/to/firmware/ \           # 固件文件根目录（用于查找 .so）
    Dlink-DI8300                   # 设备名（结果目录名）

Step 4  — 运行单个阶段

# 只运行 elf 阶段
conda run -n iotreaper python3 liva.py /path/jhttpd /path/fw/ MyDevice --stages elf

# 运行 source + sink 两个阶段
conda run -n iotreaper python3 liva.py /path/jhttpd /path/fw/ MyDevice --stages source sink

# 只跑最后的漏洞推断
conda run -n iotreaper python3 liva.py /path/jhttpd /path/fw/ MyDevice --stages infer

# 预览将要运行的阶段，不实际执行
conda run -n iotreaper python3 liva.py /path/jhttpd /path/fw/ MyDevice --dry-run

Step 5  — 运行测试套件

conda run -n iotreaper python3 -m pytest tests/ -v
# 预期：12 passed
注意： source / sink / danger 阶段依赖 IDA Pro 已打开目标二进制并运行 IDA-MCP 服务端。若 IDA 尚未打开文件，IDAMCPClient 会自动调用 tools_session.analyze_binary() 启动 IDA 工作进程（需要 IDA 授权许可），并等待最多 5 分钟直到分析完成。

05  核心组件说明

IDAMCPClient
macOS 原生 IDA Pro 接口。通过 sys.path.insert 直接导入 ida-mcp-main 项目，调用 tools_session.analyze_binary() 启动 IDA 工作进程（命名管道 IPC），再用 ida_tools.query.lookup_funcs() 查询函数地址、decompile() 获取 C 伪代码。会话按二进制路径缓存，避免重复启动。
Chatbot
LLM 对话客户端。使用 openai.OpenAI(base_url=…) 接入任意 OpenAI 协议兼容的中转 API。支持 source / sink / vul 三种对话模式，各自加载不同的系统 Prompt（session JSON 文件）。返回 bytes，与管线其余部分保持兼容。
SimplePathFinder
Neo4j 的轻量替代。读取 Ghidra 输出的 parent_child_calls_ida_decompile.json，在内存中遍历每个父函数的 child_names 列表，筛选同时调用了 source 函数集合 AND sink 函数集合的父函数，返回 VulInfer 所需格式的路径列表。
TaintAnalyzer
参数污点追踪。从 danger 阶段的反编译代码中提取参数传递片段，以 Few-shot 格式发给 Fine-tuning LLM，输出结构化的参数映射关系（谁调用了谁，哪个参数携带外部输入）。支持超时重试机制。
VulInfer
漏洞推断引擎。加载 IDA 反编译映射，按 call_chain 合并报告，拼装"source_function / sink_function / call_chain / code"格式的文本块，最终调用 LLM 判断是否存在命令注入或缓冲区溢出，写入 vul_result.txt。
DangerFuncAnalyzer
两步工作：① 调用 Ghidra DangerFlowAnalyzer.java 生成 parent_child_calls.json（调用图）；② 用 IDAMCPClient 对每个父函数地址反编译，将 decompiled_c 字段追加写入 JSON，生成最终的 parent_child_calls_ida_decompile.json。

07  各阶段输出文件

所有结果写入 result/{device}/{project_name}/，project_name 格式为 {binary_name}_{md5前6位}。

  • iot_file/ elf 阶段：主 ELF 和所有 .so 库的拷贝
  • elf_parse/library_info.json elf 阶段：依赖库列表及路径
  • mcp_source_decompile_request.json source-ghidra：需要反编译的函数列表（按库分组）
  • mcp_source_decompile_result.json source-IDA：IDA 反编译结果，{lib: {func: {code, inlined_from}}}
  • mcp_sink_decompile_request.json sink-ghidra：危险函数调用链上的函数列表
  • mcp_sink_decompile_result.json sink-IDA：Sink 相关函数的反编译结果
  • parent_child_calls.json danger-ghidra：调用图，{data: [{parent_name, parent_address, children}]}
  • parent_child_calls_ida_decompile.json danger-IDA：调用图 + 每个父函数的 decompiled_c 字段
  • taint_analysis.json taint 阶段：参数污点映射结构，{results: [{entry, result}]}
  • cmd_injection_candidates.txt infer 阶段：候选漏洞代码片段（发送给 LLM 前）
  • vul_result.txt 最终结果：LLM 判定的漏洞报告，含调用链、代码和 Yes/No 结论

08  常见问题

❌

IDA 会话无法创建

确认 ida_dir 路径正确，且 IDA Pro 有有效 License。IDAMCPClient 会等待最多 300 秒（可在 probe_timeout_sec 调整）。

❌

LLM 返回 error

检查 config.ini 中的 api_key 和 base_url 是否正确。可用 curl 直接测试端点是否可达。

❌

parent_child_calls.json 不存在

danger 阶段依赖 Ghidra 成功运行。检查 logs/GhidraAnalyzer.log，确认 Ghidra 路径 ghidra/support/analyzeHeadless 可执行。

❌

infer 阶段无路径输出

source / sink 函数集合无交集。检查 source 阶段是否成功写入 LivaConfig.source_point，或在 config.ini 的 [VulFunction] 中补充 Sink 函数列表。

❌

binary not found 错误

IDAMCPClient 在 send_multiple_libs 中查找 result/…/iot_file/{lib}。确认 elf 阶段已成功将库文件拷贝到该目录。

✅

从某个阶段继续

可以只指定后续阶段，例如 --stages taint infer。每个阶段都读取前一阶段已保存到磁盘的 JSON 文件，支持断点续跑。
